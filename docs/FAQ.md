# 常见问题（FAQ）

## Token 统计：「缓存写入」为什么永远是 0？

**结论：这个 0 是真实值，不是统计缺陷。**

Token 统计页「Token 与调用趋势」里的 `缓存写入` 系列（以及导出里的「缓存写」列）在 WorkBuddy
数据源上恒为 0（0.0%），近 30 天合计 9.9B Token 时同样如此。原因是上游数据里根本没有这个量：

| 证据 | 数据 |
| --- | --- |
| 数据源 | `~/.workbuddy/projects/**/*.jsonl`，774 个文件 / 2.28 GB |
| `usage` 对象只有 4 个键 | `input_tokens` / `output_tokens` / `total_tokens` / `cache_read_input_tokens` —— **没有写入字段** |
| 写入字段只出现在 `providerData.rawUsage` | `prompt_cache_write_tokens`、`cache_creation_input_tokens`、`cache_write_tokens` |
| 全量扫描结果 | 183,613 条记录，`prompt_cache_write_tokens` 与 `cache_creation_input_tokens` 的最大值**均为 0** |
| 解码器口径正确 | `crates/wb-shift-core/src/modules/token_stats/projection.rs` 的 `CACHE_WRITE_KEYS` 覆盖上述四个别名；单测 `cache_write_uses_explicit_aliases_but_never_cache_miss` 钉死「不得把 `prompt_cache_miss_tokens` 当写入」 |
| 旁证 | 同批数据 `cache_read_input_tokens` 正常（1.3B、命中率 98.5%），说明上报链路是通的 |

DeepSeek 系的上下文缓存是**自动命中、按命中/未命中计价**，没有 Anthropic 式的「cache write」
计费项；WorkBuddy 的 `rawUsage` 保留这些字段只为 schema 兼容，在 DeepSeek 模型上从不填值。

### 为什么不隐藏这一列？

- 用户已明确选择**保持现状**：继续显示「缓存写入」系列与 0 值，不做自动隐藏、不加说明 tooltip。
- 若将来接入会上报缓存写入的模型（例如 Anthropic 系），该系列会自动出现非 0 值，**无需改代码**；
  届时再讨论「恒 0 时隐藏」才有意义。

### 相关维护规则

1. **不得**因为恒 0 删除 Rust 侧的写入解析（`CACHE_WRITE_KEYS` / `usage_fields` / `usage_from`）。
2. **不得**用 `prompt_cache_miss_tokens` 冒充写入量：它表示「新计算的（未命中缓存的）输入」。
3. **导出列必须与图表系列一一对得上**：图上有哪个 token 分类，导出就有哪一列。
   注意映射不是字面同名——导出「输入」列 = 图表「新增输入 + 缓存读取」（`input` 已含 `cacheRead`）；
   「总 Token」「请求数」是合计/计数列，不对应单个系列。任一侧增删分类都必须同时改另一侧
   （`src/pages/token-stats/trend-chart.tsx` 的 `TOKEN_SERIES` ↔ `src/pages/token-stats/export.ts`
   的 `TOTALS_HEADERS` / `totalsCells`）。
4. 计算口径 `total = input + output + cacheWrite` 不变：`cacheWrite` 恒 0 时对结果无影响。

### 想自证链路是通的？

构造一条 `prompt_cache_write_tokens > 0` 的 jsonl 再跑一次统计，界面与导出的「缓存写入」会显示
非 0 —— 说明解析与导出链路可用，只是源数据没有这个值。

### 注意范围

本结论只针对 WorkBuddy 数据源。本机没有 CodeBuddy CLI 数据（`~/.codebuddy/projects` 不存在），
IDE 的 `cacheWriteInputTokens` 路径未参与实测；若那份数据里有非 0 值，属于正常情况。

## Token 保活多久？需要多久重新登录一次？

**结论：没有固定天数，也不承诺天数。**

用的是 access + refresh 双令牌，续期有**两条路径**，两条都在跑：

1. **按需惰性续期**：真正要用令牌时才看 access 的剩余有效期——查积分、签到（含状态核验）、
   派猫猫旅行都会先过这一道闸（`refresh.rs` 的 `ensure_fresh_token`）；账号页手动「Token 刷新」
   与接口回 401 时则直接调 `refresh_account_token` 补刷一次。剩余有效期少于设置页
   「自动签到 → 惰性刷新」（`lazy_refresh_hours`，默认 24 小时）、已过期或没有 `expiresAt`
   才用 refresh 换新的；用不到就不刷新。
2. **后台保活**：应用**每次启动立刻跑一轮**，之后**每天一次**（`src-tauri/src/lib.rs` 的
   `last_keepalive_day` 逻辑 → `refresh.rs` 的 `run_keepalive_cycle`）。每轮遍历全部账号，
   实际刷谁由设置页「自动签到 → 保活阈值」（`keepalive_days`）决定：
   - 阈值 **`0`（默认）**：**无条件刷新全部**带 refresh token 的账号；
   - 阈值 **`> 0`**：只刷新「剩余有效期不足该天数」的账号（含已过期、`expiresAt` 缺失）。

为什么要有后台保活，而不只靠惰性续期：官方服务端会清理长期闲置的 refresh 会话，闲置久了
刷新会直接返回 `12153 invalid_grant`（Session doesn't have required client），账号被迫重新登录。
保活让令牌一直处于「刚被用过」的状态。代价是每天都会打接口，而且**可能与官方客户端同时刷新**——
refresh token 是轮换的，谁后刷谁手里的旧令牌就作废。

这个代价已经处理过，**当前登录的账号不再被抢刷**。打刷新接口之前先读官方客户端的认证文件，
按读到的结果三选一：

- 同一个账号**且那边凭据确实更新**（`lastRefreshTime` / `expiresAt` 更新）→ 只把新凭据
  **回填账号库（adopt）**：**不发刷新请求、也不写回认证文件**；
- 认证文件存在但**读不出来**（客户端正在写）→ **跳过本轮**：不发请求、不改账号库，
  也**不**判定为「需重新登录」；
- 该档位没有登录的官方客户端，或读到的不是同一个账号 → 与改造前一致，照常刷新。

「多久要重登」取决于官方对 refresh 的有效期与吊销策略，这个是官方侧决定的，工具承诺不了。
能保证的是：只要 refresh 还有效，就不需要你手动重登；refresh 失效时会在界面上标「需重新登录」，
不会静默失败。

## 为什么反复弹出「访问系统钥匙串」？

**结论：这是只读访问 VS Code 的 Safe Storage，不是写入，也不会把凭据传出去。**

反复弹的原因不是工具在反复索取：点「拒绝」时 macOS **不会记住**这个决定，所以下次仍会问。

三种处理方式：

1. 不用 VS Code 插件（只用 CodeBuddy IDE / WorkBuddy，这两条路径不读 Safe Storage）；
2. 弹窗里点「始终允许」，输入一次登录密码；
3. 手动在「钥匙串访问」里给该应用授权。

## 限额标记是怎么来的？为什么有时不显示？

限额数据只有两类来源：

| 来源 | 覆盖 | 精度 |
| --- | --- | --- |
| hook 实时上报 | CodeBuddy CLI、WorkBuddy 客户端 | 最准，命中即报 |
| 本地日志扫描 | 两个 CodeBuddy IDE | 按文件 mtime 收窗，5 分钟节流并缓存 |

两点边界：

- **VS Code 插件宿主**的 429 记录落在 `exthost/<插件>/` 下，两个 IDE 的目录里没有；该来源
  **暂不支持**（插件不写可解析的限额日志，也没有等价的 hook），需求已转上游 issue #188，
  与设置页「限额监听」里的说明一致。该处的「诊断信息（日志探针）」**只采样、不判定限流**，
  不会因此多出任何限额条目。
- 卡片显示「暂不支持」表示当前账号的来源不在覆盖范围内，**不是配置问题**。

## 用免积分模型，为什么积分不变？

**结论：不是 bug。** 国际版的 `dsf4.1` 本来就是免积分模型，用它消耗 0 积分。

Token 侧的数字从 0.2.1 起拆成 6 个来源分别统计，之前混在一起才会看起来「统计不全」。

## 复制或同步会话后，会话详情里的「共消耗」为什么不是两边相加？

**结论：不是丢数据，是归属口径——哪个账号用的积分，就记在哪个账号上。**

复制会话只搬聊天正文（和中断记录），**不搬会话的用量账本**（`session_usage`）；同步本来也不搬。
所以历史消耗始终留在来源账号，副本从 0 开始只记自己的新增：

| 数据 | 复制 | 同步 |
| --- | --- | --- |
| 聊天正文 / 中断记录 | 拷贝到副本 | 增量同步 |
| 会话用量（客户端会话详情里的「共消耗」） | **不搬**，副本只累计自己新增的消耗 | **不搬**，目标账本保持原样 |

几点要知道的：

- 来源账号 A 的历史消耗永远归 A，副本 B 只累计复制之后 B 自己用掉的量；
- 客户端会话详情里副本的「共消耗」会显示 **0 或明显偏少**（两种都可能，取决于客户端有没有用量行），
  这是预期行为，不是复制失败；
- **「共消耗」不可按账号相加**：把各账号副本的数值加起来，会把同一段历史重复计数或干脆漏算；
- 想看某个账号到底用了多少，请看本工具的**「积分统计」**：它按账号汇总官方请求用量，
  没有会话维度，复制 / 同步前后数字不变。

> 说明：0.5.0 及更早版本的发布说明里「复制会话时一并带上用量账本」已不再适用——复制与同步都不搬历史消耗，
> 那是按「谁用的记在谁头上」重新定的口径。

## 账号会不会被封？出问题怎么自查？

**结论：本工具不会替你「伪造活跃」，但也不能保证账号不被风控。** 是否受限取决于官方策略。

这个工具**做**的：切换账号、共享本机登录态、复制会话/置顶/记忆、显示限额与积分、保活刷新令牌。
这个工具**不做**的：定时发请求制造在线假象、批量注册/养号、绕过官方限流、代答权限审批。

如果账号出现异常，按顺序自查：

1. 是否在多个工具/脚本里同时使用同一个账号（并发刷新最容易把令牌打乱）；
2. 是否在短时间内高频切换（切号会重启客户端，属于明显的客户端行为）；
3. 官方客户端里能否正常登录 —— 如果官方也登不上，问题在账号侧，不在本工具；
4. 保留日志与时间点，向官方反馈时一并提供。

工具侧能做的只有一件事：出问题时**不掩盖**——刷新失败会分级（临时错误 vs 明确吊销），
不会把网络问题写成「账号失效」。

## 能从其它工具导出的号池 JSON 导入吗？

**结论：能，但只有带明文完整凭证的导出可以；显示「加密池密文」或「缺少 token」的文件导入后会整条跳过。**

导入弹窗读的是账号列表，支持两种顶层形状：

| 形状 | 示例 | 说明 |
| --- | --- | --- |
| 数组 | `[{"uid": "…", "access_token": "…"}]` | 本工具自己的备份格式 |
| 包装对象 | `{"accounts": [ … ]}` | 第三方号池工具常见格式（其余顶层键忽略） |

凭据字段兼容 camelCase 别名，规范键优先：

- `access_token` ← 其次是 `accessToken`，再其次是 `token`；
- `refresh_token` ← 其次是 `refreshToken`；
- 已经有合法 `access_token` 时**不会**被别名覆盖；其它字段原样保留（不裁剪、不改名）。

三类文件导不进来，预览里会给出对应徽标：

1. **缺少 token**：脱敏分享导出（只含昵称/邮箱/uid），凭证被对方刻意剥掉了；
2. **加密池密文**：`access_token` 是 `enc:v1:` 开头的密文，只有对方工具能解，本工具既不当作有凭据、也不会写进账号库；
3. **空串 / 普通对象**：`"access_token": ""` 或 `"access_token": {"token": "…"}` 都不算凭据。

**正确做法**：在对方工具里选择「导出明文完整凭证 / 包含 access_token 与 refresh_token」的导出项，
再回到「导入账号」选择该文件；预览里每条都显示为可勾选（没有红字徽标）时导入才有效。若对方只提供
`enc:v1:` 密文，说明它不支持把凭证交给别的工具，只能放弃导入。
